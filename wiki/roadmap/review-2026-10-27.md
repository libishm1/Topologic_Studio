# Topologic Studio Next — review of fire egress, simulation and RL

Date: 2026-10-27
Audience: the maintainer, and any follow-on agent
Branch: `next/studio-2` (worktree `TopologicStudio-Next/`). Classic untouched.
Builds on: [handoff-2026-08-24.md](handoff-2026-08-24.md),
[pages-deployment-options-2026-09-21.md](pages-deployment-options-2026-09-21.md)

---

## 1. Summary

- **RL training was broken in practice and is now fixed.** Five separate
  defects, each small, together meant the agent could not reach the exit on a
  real floor plan. After the fixes it finds the A*-optimal route on a
  3,111-node floor in 66 ms, and escapes a tight fire race in 20 of 20 seeds,
  where the old code managed 0 of 20.
- **The temperature fire model had a real numerical bug.** Any node stored
  directly before an isolated node heated twice as fast as Classic's formula.
  Fixed, with a test against Classic's own loop.
- **Live rerouting now works with every fire model**, not only `temperature`.
- **The backend's compute was never the slow part of the hosted site.** A
  route query costs 3 ms of search. The live site's first request took
  **33.1 s** (free-tier wake-up), and each warm request after that about 0.3 s,
  mostly the round trip to Render's default Oregon region. Code changes cut
  request time about 2×; plan and region are the levers that matter, and both
  need an account-owner decision (section 5).
- **TopologicPy moved to 0.9.86, not the newer 0.9.87.** 0.9.87 deletes the
  legacy `topologicpy.Graph` module, which would silently remove
  `/upload-topology`.

Backend tests went from 83 to 95, all passing. The real-Chrome browser suite
passes 30 of 30 steps with 0 console errors, 0 page errors and 0 failed
requests.

### TopologicPy 0.9.72 → 0.9.87 (released 2026-09-21 to 2026-10-23)

Taken from the wheels on PyPI, compared by source. Nothing here was taken on
trust from release notes alone.

### Syntopy (syntopy.io)

This is a consultancy, not a backend. Its site says TopologicPy, TopologicDepth,
TopologicJourney and TopologicExplore are "products of Syntopy"; the source
carries Wassim Jabi's copyright. Its four hosted apps sit behind a login, and it
publishes no public API Studio could call. **Nothing to switch to.**
Its 16 tutorials were verified on 0.9.86 with the PythonOCC backend. They use
`TGraph` only, never the legacy `Graph`, and none covers egress, fire, agents
or RL.

### ModRes (github.com/emmashelley/ModRes)

A cleaned ResPlan dataset: 8,431 apartment plans, each with adjacency,
accessibility and full dual graphs. MIT licence (ResPlan's own licence should
be checked before redistribution). Its notebooks use the legacy `Graph` API, so
they will not run on 0.9.87. There are no simulation or RL methods in it.

### LOD1 Topologic model (`CM-iTAD/Shoaib_masters/LOD1_TopologicModel`)

This is the lab's most current TopologicPy codebase. It pins **0.9.86 with
`topologic-core` 8.0.4**, the same choice made here independently. It builds
one Cell per room and the building as one CellComplex, exports circulation and
adjacency graphs, and draws ModRes plans as a training corpus. Two of its ideas
carry over:

- **"One question, several simulators"** (`lod1/simulators.py`): EnergyPlus, a
  learned surrogate and a web service behind one `available()` / `run()`
  interface. Studio's path engines already follow this shape; RL and any future
  agent-based model should join the same interface rather than grow their own.
- **Canonical node order** (`lod1/graphs.py`): TopologicPy may emit nodes in a
  different order on each run, which makes anything learned on them
  non-repeatable. That matters for any future graph-ML on Studio's graphs.

## 3. Findings and fixes

Severity: **H** = produces wrong results, **M** = misleading or slow,
**L** = cosmetic or doc.

### Fire

| # | Sev | Finding | Fix | Test |
| --- | --- | --- | --- | --- |
| F1 | H | `temperature_steps` summed neighbours with `np.add.reduceat`, with isolated nodes' offsets zeroed. `reduceat` reads a non-increasing offset as "take one element", so a node stored directly before an isolated node summed only its **first** neighbour. On a 4-node repro, node 0 read 80 °C where Classic's formula gives 50 °C. | `np.bincount` keyed by CSR row. | `test_temperature_matches_classic_with_isolated_nodes`: random graph with interleaved isolated nodes, compared step by step against Classic's loop. |
| F2 | M | Live rerouting was `temperature`-only, so the `flood` model, the one whose front walls actually shape, never rerouted. | `flood` and `radial` reroute with burning nodes impassable, falling back to a walls-only route with a note when the fire has cut every route. | `test_flood_stream_reroutes_around_burning_nodes` |

### RL (`graphs/rl.py`, `/api/rl/train`)

| # | Sev | Finding | Fix |
| --- | --- | --- | --- |
| R1 | H | The fire was seeded at the **evacuee's own start node**. A flood front moving one hop per step then chased the agent at exactly its own speed, so any exploratory move ended the episode. The frontend already had a fire-origin picker and never sent it. | `fire_point` / `fire_id` on the request, sent from the picker. With no origin the policy trains fire-free, and the response says so. |
| R2 | H | `gamma = 0.9`. The +10 exit reward 75 hops away is worth 0.004, so the agent could not see the exit. | `gamma = 0.99`, exposed on the request. |
| R3 | H | Terminal transitions bootstrapped from the next node's Q row. | No bootstrap on terminal transitions. |
| R4 | H | The agent ignored walls, so its route crossed edges A* refuses. | Uses the same blocked mask as A*. |
| R5 | H | The state was the node alone while the fire made reward time-dependent. On a tight race the agent pinned −10 on the only escape corridor (0 of 20 seeds escaped). | The state is `(node, step)` when there is a fire, and the node alone when there isn't. |
| R6 | M | The reported "reward" was a sum of Q-values, and the rollout never checked for fire. | Real undiscounted return; `burned` flag. |
| R7 | M | Exploration was blind on large graphs. | Potential-based shaping on the walls-respecting distance to the exit (Ng, Harada & Russell 1999), plus untried actions initialised to their one-step shaped value. Neither changes which policy is optimal. |
| R8 | M | Step cost was per hop, so RL optimised hop count while A* optimises metres. | Step cost is proportional to edge length. |
| R9 | M | Nothing distinguished "failed to learn" from "nothing to learn". | `escape_steps` from an exact earliest-arrival BFS (exact because the fire only grows), plus a `note` the UI shows. |

| Scenario | Old | New |
| --- | --- | --- |
| 12×12 grid, fire race with a 1-step margin, 20 seeds | 0/20 escape | 20/20, all on the optimal route |
| 12×12 corner to corner, no fire, 20 seeds | 20/20 | 20/20, all optimal |

### Speed (backend)

| # | Finding | Fix |
| --- | --- | --- |
| P1 | Every path, fire and RL request ran a pure-Python connected-components BFS. It was 11 of the 14 ms a route query took. | Computed once with `scipy.sparse.csgraph` and cached on the immutable `NavGraph`. |
| P2 | `graph_stats` ran two more of those BFS passes per build. | Uses the cache. |
| P3 | `edge_block_mask` was a Python loop over every edge. | One KD-tree query for all walls, then one vectorised crossing test. Bit-identical masks, checked on random data for both up axes and on a realistic graph (2,735 of 38,275 blocked either way); 114 → 40 ms with eight 20–30 m walls, about 10× with one. |
| P4 | `ifcopenshell>=0.8.4` was unbounded. The Linux image would resolve **0.9.0** while every test ran on 0.8.5. | Capped `<0.9`. |
| P5 | The image installed `build-essential` "in case a wheel is missing". | Removed. A dry-run resolve for Linux CPython 3.12 confirmed all 51 packages ship wheels. The build itself was **not** run: no Docker on this machine. |

## 5. Decisions for the human

These are research-validity or account calls, so none of them was made here.

1. **Time model (the biggest one).** Fire and evacuee both advance one *hop*
   per step, but edges range from 0.5 to 2.25 m, and RL now (correctly)
   optimises metres. A fire race therefore rewards the fewest-hops route,
   while the agent prefers the shortest-metres route. On a 3,111-node floor,
   races with an escape of exactly 51 moves were never learned. The physical
   fix is metric time: the evacuee's time is walked distance ÷ walking speed,
   and the fire front is graph distance ÷ spread rate. That changes the model,
   so it is proposed here, not implemented.
2. **Fire speed.** Classic's implicit ratio is 1.0: the front moves as fast as
   the evacuee. On a 30 × 25 m floor, three different fire origins all left
   **no** escape at 1.0. `fire_speed` is now exposed with the Classic default,
   and the result states when nothing could be learned. Choose a defensible
   default (or a metric rate, see 1).
3. **The evacuee stands still during live rerouting.** Each recompute solves
   from the original start, as if the person had not moved since step 0. This
   is inherited from Classic. A walking evacuee is the obvious extension and
   needs the same time unit as (1).
4. **Temperature model.** (a) A degree-1 node overshoots its own neighbour,
   because `heat_transfer / degree = 1.2 > 1`. Inherited from Classic's
   formula; left as is for comparability. (b) The model caps at 120 °C, below
   flashover; 120 is a "fire source" constant rather than a physical
   temperature. The lethality threshold UI reads in °C, so the two should be
   reconciled before anyone quotes a temperature from it.
5. **Hosting.** In order of effect:
   - **Plan:** Render `starter` removes the 33 s wake-up. On the free plan, an
     uptime pinger can keep *one* service awake, but the 750 free hours are per
     workspace, so Classic and Next together run out mid-month.
   - **Region:** `render.yaml` now asks for **Frankfurt**. Region is fixed at
     creation, so this only applies to the Next service when it is first
     created.
   - **Publish:** preview vs merge is still the open question from
     [pages-deployment-options-2026-09-21.md](pages-deployment-options-2026-09-21.md).
     Nothing public was changed.

## 7. Adopted after the review (same day)

### Alternative routes: `POST /api/ifc/path/alternatives`

`TGraph.KShortestPaths` ships in **0.9.87**, which Studio cannot take yet (it
removes `Graph`; see above). So Yen's algorithm is implemented in
`graphs/alternatives.py` on the built-in A*. When the installed TGraph has
`KShortestPaths` and the TopologicPy engine is selected, the call is delegated
to it. That hand-off was tested against a real 0.9.87 install in a throwaway
venv: the same route costs as the built-in Yen, 13/13 tests.

Yen turned out to answer the wrong question on a navigation lattice. On the
Duplex (upper floor to a ground-floor door), the 2nd to 5th routes were all
19.17 m, exactly the best route's length, and lay entirely within 1.5 m of it:
ties, not alternatives. So the default is a second method, **distinct**:

- **Method:** a penalty method (Akgün, Erkut & Batta 2000). Edges within
  1.5 m of each route found get dearer, and the search runs again.
- **Acceptance:** a route is kept if at most 50% of it runs within 1.5 m of a
  better route and it is at most 1.5× the shortest.
- **Overlap:** measured spatially, because two lattice routes can share no
  edge and still run down the same corridor.

Same query: **19.17 m and 27.40 m** (12% shared), and the API says no third
route exists within 1.5×; 53 ms. On the browser suite's short route, there is
only one way. Fewer routes than asked is reported as a finding, not an error.
Yen stays available as `method: "yen"`.

### Navigation cross-check: `POST /api/ifc/navigation-check`

The browser sends the IFC, and the server builds TopologicPy's own
`Navigation` graph of it and compares the two.

**Getting both graphs into one frame took a detour.** A translation-only fit
(ICP) slid 0.15 m along the lattice. It cannot tell a true offset from a
partial grid step, nor which storey is which when only one graph has a floor.
That Open's `model.getCoordinationMatrix()` turned out to be exactly the shift
web-ifc applied with `COORDINATE_TO_ORIGIN`: a pure translation (−2.514,
−3.262, −11.635) on the Duplex. Adding the 0.75 m agent lift, it matched the
fit to 2 mm on the two axes the lattice pins down. The browser now sends the
matrix and the server uses it exactly. The fit remains only as a labelled
fallback.

Duplex, 0.5 m spacing, browser suite run:

| | Value |
| --- | --- |
| Navigation graph | 2,603 nodes, 9,281 edges, **20 separate parts**, 62 stair-tread nodes |
| Build | 7.9 s cold through the API (parse 3.8 s + grid 3.5 s locally); grid only when cached |
| Alignment | coordination matrix, median gap 0.21 m |
| Its nodes our graph covers (within 0.5 m) | **99%** (Level 1 99.9%, Level 2 98%) |
| Our nodes it covers | **91%** (Level 1 99%, Level 2 **79%**) |
| Route, same start and exit | ours 5.76 m, its 6.24 m (1.08×) |

The Level 2 gap is 145 of our floor nodes in seven small bands. Their median
distance to Navigation's nearest node is 0.54–0.60 m, just outside the radius.
That reads as the two graphs drawing the walkable edge differently, not a
missing room. Which one is right is a question for the model (next work, 6).
On Render's free CPU share the build will be much slower than 7.9 s; the
client waits up to 5 minutes.
